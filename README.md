> Automatically re-sign ChromeOS images on repack<br>Instead of requiring scripts to detect ChromeOS images and sign them<br>after repacking, preallocate the vblock and append the kernel blob<br>trailer while repacking, then generate the vblock after all other<br>patching is done. The image is padded to its original size after<br>signing, same as other boot images.<br>The signer now only takes the kernel payload and returns the vblock,<br>hashing the kernel blob incrementally. The sign-chromeos action<br>streams its output to disk instead of building the whole signed<br>image in memory.<br>Since ChromeOS images no longer need special handling, unpack no<br>longer returns 2 for them, and all ChromeOS logic is removed from<br>the scripts.<br>Assisted-by: Claude Opus 5.5

> Sign ChromeOS boot images with magiskboot<br>Port the `futility vbutil_kernel --pack` code path used to sign<br>ChromeOS boot images into magiskboot as a new `sign-chromeos` action.<br>The kernel keyblock and data key are embedded into the executable, and<br>all signing parameters previously passed in sign_chromeos are<br>hardcoded. The output is bit-for-bit identical to the reference tool.<br>Rename the existing `sign` action to `sign-avb1` to disambiguate.<br>Remove the prebuilt futility binary and stop shipping the chromeos<br>assets folder; scripts now call magiskboot directly.<br>Assisted-by: Claude Opus 5.5

> app: add WholeFilePatcher and ImageExtractor<br>Define WholeFilePatcher and ImageExtractor interfaces for whole-file<br>patching and single-image extraction pipelines.<br>Have TarProcessor implement WholeFilePatcher, and OtaPayloadExtractor<br>and ZipExtractor implement ImageExtractor. > app: share one input pipeline for files and URLs<br>processFile handled two different jobs in one function, sharing<br>variables and try/catch blocks: patching a tar archive into a new tar,<br>and extracting a boot image into a patched .img. It also opened the<br>input twice, as a stream for detection and as a channel for the<br>extractors. processUrl separately repeated a zip-only copy of the<br>image path.<br>Open the input once as a DataChannel: DataChannel.File for a URI and<br>DataChannel.Http for a URL. Everything after that is one pipeline:<br>processInput reads the header with a positional read and dispatches to<br>processArchive (tar in, tar out) or extractAndProcessImage (payload,<br>zip or raw image in, image out). As a result, URLs now accept every<br>format that files do.<br>Additionally:<br>- Rename DataChannel.sliceStream to stream, and add a zero-arg<br> stream() that covers the entire channel.<br>- Make TarProcessor.consume take a DataChannel and close it, matching<br> the extractors.<br>- Close the input ParcelFileDescriptor instead of leaking it.<br>- Report output file creation failures on the URL path instead of<br> crashing.<br>Assisted-by: Claude Opus 5.5

> app: extract tar processing into TarProcessor<br>Tar firmware handling (e.g. Samsung AP tars) was entangled with<br>MagiskInstallImpl: BootItem and processTar lived in the installer, and<br>processFile set up the TarArchiveOutputStream, used a nullable<br>BootItem as the tar flag, and reassigned its file to new-boot.img.<br>Move all tar logic into a standalone TarProcessor next to<br>OtaPayloadExtractor and ZipExtractor. Since the output tar has to stay<br>open while the installer patches the image, it uses a two-phase API:<br>consume() extracts the boot images, copies all other entries to the<br>output tar, and returns the image to patch; finish() writes the<br>patched image and finalizes the archive. The caller still owns and<br>closes both raw streams, and MagiskInstallImpl no longer references<br>any tar types.<br>Additionally:<br>- Pass through vbmeta.img smaller than 256 bytes unpatched instead of<br> looping forever, as the loop continued without advancing the entry.<br>- Close the output stream when patching fails instead of leaking it,<br> ignoring close errors so that they cannot crash the app.<br>Assisted-by: Claude Opus 5.5

> app: refactor DataChannel and extractors<br>Refactor DataSourceChannel into an abstract DataChannel with nested<br>DataChannel.File and DataChannel.Http implementations, separating<br>local file and remote HTTP stream backends.<br>Additionally:<br>- Rename Payload to OtaPayloadExtractor and ExtractImage to<br> ZipExtractor to better reflect their responsibilities.<br>- Standardize both extractors with a uniform constructor and a<br> consume(channel: DataChannel) method that handles channel lifecycle.<br>- Make OtaPayloadExtractor stateless by passing channel, manifest,<br> and data offsets directly through method arguments.<br>Assisted-by: Gemini 3.8 Flash
