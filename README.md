> app: keep Home dialog state across recreation<br>Two Home dialogs didn't restore their data with their visibility:<br>- The "abnormal state" dialog kept its visibility in saved state but<br> its exit code in plain remember. > app: request notification permission for updates<br>Turning on "Check for updates" didn't request the notification<br>permission, so on Android 13+ the update notifications could never be<br>shown. Instead, every creation of MainActivity, including rotations,<br>requested the permission when the setting was on, and turned the<br>setting off if it was denied, while the settings switch still showed it<br>as on.<br>Request the permission when the setting is turned on, and only enable<br>it when granted. Only request it on startup when the activity is first<br>created, and refresh the switch from the setting when the settings tab<br>resumes.<br>Assisted-by: Claude Opus 5.5

> app: handle errors when saving logs<br>Saving the install, action or Magisk log didn't handle any error: if<br>creating or writing the file failed (e.g. storage full, or the media<br>store rejecting the file), the exception reached the default handler<br>and the app exited. On Android 10 and older, a module name containing<br>a slash also made the action log name point to a missing directory.<br>Save logs through a shared helper that replaces slashes in the name<br>and shows an error toast when saving fails.<br>Assisted-by: Claude Opus 5.5

> app: recreate activity on locale change<br>Without the system's per-app language settings (before Android 13),<br>changing the language in the app relaunched the foreground activity by<br>starting it again and finishing it. MainActivity is singleTask, so the<br>start was delivered to the same instance, which was then finished, and<br>the app closed instead of showing the new language.<br>Recreate the activity instead, and remove relaunch(), which has no<br>other users.<br>Assisted-by: Claude Opus 5.5

> app: remove legacy isolated denylist entries<br>Isolated processes are matched by name prefix, and the DenyList now<br>adds a single "isolated|<process>:" entry per app. Older versions of<br>the app added one entry per isolated service instead, e.g.<br>"isolated|com.foo:com.foo.Service". The screen shows the isolated row<br>as checked if any entry starts with the prefix, but unchecking it only<br>removed the exact prefix entry, so the old entries stayed and the row<br>was checked again on the next visit.<br>When removing an isolated row, remove every isolated entry starting<br>with its prefix.<br>Assisted-by: Claude Opus 5.5

> app: serialize superuser grant writes<br>Each tap on the grant screen started its own database write on the IO<br>dispatcher, with nothing ordering them. A grant takes two queries<br>(fetch, then replace) while a revoke takes one, so a quick grant and<br>revoke could run as fetch, delete, replace and leave the app granted<br>while it was shown as not granted. The new state was also computed from<br>the item the UI captured, so two taps before a recomposition both<br>granted.<br>Write in tap order under a Mutex, like SuperuserViewModel does, and<br>toggle the current state of the app.<br>Assisted-by: Claude Opus 5.5

> app: keep lists while refreshing<br>The superuser, log and module lists are refreshed whenever their tab is<br>shown, when returning to the main screen, after configuration changes,<br>and on other events (the module list on every activity start, the logs<br>on every superuser request). Each refresh set the loading flag, which<br>replaced the list with a spinner, so the list lost its scroll position<br>and expanded cards collapsed. Module update buttons also disappeared<br>until update info was fetched again. The DenyList even scanned every<br>installed app again on rotation.<br>Only show the loading state until the first load finishes, keep update<br>info of unchanged modules across refreshes, and scan apps for the<br>DenyList only once per screen.<br>Assisted-by: Claude Opus 5.5

> app: run module actions in BusyBox ash<br>Every script running in the context of Magisk is supposed to run in<br>BusyBox ash with standalone mode. Since module actions and installs run<br>in a PTY, they ran in /system/bin/sh instead: busybox script starts<br>$SHELL, which su sets to /system/bin/sh, and ASH_STANDALONE was never<br>set. Module installers recover by re-executing themselves in BusyBox,<br>but action.sh has no such fallback.<br>Run the PTY command in BusyBox ash with ASH_STANDALONE=1, which has to<br>be set before ash starts. Also run the action from the module's<br>directory name, quoted, rather than from the id in module.prop, which<br>can differ from it.<br>Assisted-by: Claude Opus 5.5

> app: release the installer lock when cancelled<br>MagiskInstaller.exec() only cleared its static session flag after the<br>operation returned normally. When the calling coroutine was cancelled,<br>withContext() threw once the blocking operation finished and the flag<br>stayed set, so every later install, patch, uninstall, restore or<br>environment fix failed immediately until the app process died.<br>Restore images and Fix environment ran in a composition scope through<br>rememberLoadingDialog(), so this happened just by rotating while their<br>loading dialog was showing, which also lost the result toast and the<br>reboot after fixing the environment. Leaving a running flash screen<br>triggered it too.<br>Release the flag in a finally block, and run both operations in<br>HomeViewModel, which survives configuration changes. Remove<br>rememberLoadingDialog(), which has no other users.<br>Assisted-by: Claude Opus 5.5

> app: don't crash on broken module metadata<br>Modules are third-party, but some of their metadata could crash the<br>app:<br>- A malformed updateJson URL (e.g. ftp://) made Retrofit throw<br> IllegalArgumentException, which LocalModule.fetch() didn't catch, so<br> the app exited every time the module list loaded, even offline. A<br> malformed changelog URL did the same when opening the update dialog.<br>- Two module directories with the same id in module.prop crashed the<br> module list, which used the id as the item key.<br>Catch every non-cancellation exception when fetching update info and<br>changelogs, and identify modules by their directory name, which is<br>unique.<br>Assisted-by: Claude Opus 5.5

> app: don't pass file names through the shell<br>The module zip's display name and path were pasted into the root shell<br>command that runs the installer, inside single quotes. The display name<br>comes from the content provider, which belongs to another app for<br>external install requests. A name with an apostrophe broke the install,<br>and a crafted name could run arbitrary commands as root.<br>Print the header line directly to the terminal instead of with echo,<br>without control characters, and quote the paths with a new<br>shellQuoted() helper, which also replaces the manual escaping in<br>runSuCommand.<br>Assisted-by: Claude Opus 5.5

> app: report real exit codes of terminal commands<br>Module installs and actions run in a PTY through busybox script, which<br>always exits with 0. The exit code of the command itself was lost, so<br>a failed module install or action was shown as done, with a reboot<br>button.<br>Run the command in a subshell and have it write its exit code to a<br>temporary file, then read it after the process exits.<br>Assisted-by: Claude Opus 5.5

> app: switch tabs on new intents<br>MainActivity is singleTask, so an intent sent while the app is running<br>is delivered to onNewIntent(). The requested tab was only read from the<br>launch intent, so e.g. the "App settings" button in the system settings<br>brought the app to the front without opening the Settings tab.<br>Also read the requested tab from new intents and switch to it. If<br>another screen is open, it stays open and the tab is shown when going<br>back, so no running flash or action screen is interrupted.<br>Assisted-by: Claude Opus 5.5

> app: don't rerun flash and action jobs on restore<br>The back stack survives process death, but a flash or action screen's<br>ViewModel doesn't. When such a screen was restored, its new ViewModel<br>had no job yet, so the job started again without the user asking: a<br>Magisk install, a module zip, an uninstall, or a module's action<br>script, which may not be safe to repeat.<br>Record in the ViewModel's SavedStateHandle that the job was started.<br>If a restored screen finds the flag in a new ViewModel, its job and<br>output are gone, so leave the screen instead of running the job again.<br>Assisted-by: Claude Opus 5.5

> app: buffer navigation events until collected<br>ViewModels requested navigation through a SharedFlow without replay, so<br>a request was silently dropped when no screen was collecting it. This<br>happens when an activity result arrives right after the activity was<br>recreated: the launcher delivers it before the screen's collector has<br>started. E.g. after a configuration change while picking an image to<br>patch, the patch dialog closed but the patching screen never opened.<br>Use a buffered Channel instead, so requests wait for the collector.<br>Assisted-by: Claude Opus 5.5

> app: drop navigation clicks during transitions<br>Clicks that open a screen were handled even while a screen transition<br>was running, so a quick second tap could push another screen on top of<br>the one being opened, e.g. an app's details and then the grant screen.<br>Wrap these clicks in dropUnlessResumed, as the Navigation 3 recipes do.<br>NavDisplay caps each scene's lifecycle at STARTED until its transition<br>settles, so taps during the animation are dropped.<br>Assisted-by: Claude Opus 5.5

> app: ignore duplicate pushes of the top route<br>Navigator.push() accepted any route, so a double tap (e.g. on an app in<br>the Superuser list) or the same flash request confirmed twice pushed<br>the same route twice. Navigation 3 gives equal routes the same content<br>key, so both copies shared one ViewModel and saved state: a second<br>identical flash request just showed the first one's result, and two<br>back presses were needed to leave.<br>Ignore a push of the route that is already on top. Making routes unique<br>instead would let a double tap start two installs at once.<br>Assisted-by: Claude Opus 5.5

> app: never pop the root navigation entry<br>A screen's back button stays clickable while the screen slides out, so<br>tapping it twice quickly called Navigator.pop() twice. The second call<br>removed Route.Main, and NavDisplay crashed the app because its back<br>stack must not be empty.<br>Make pop() a no-op on the root entry. Leaving the app from the root is<br>handled by the system, not by popping the last entry.<br>Assisted-by: Claude Opus 5.5
