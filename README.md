# Magisk (1445d83a) (31000-41)

> Make recovery image patching show progress in UI

> app: jump on long scrollbar drags<br>Dragging the scrollbar thumb of a lazy list or grid scrolled by the<br>dragged distance, and a large scrollBy composes and measures every<br>item in between. On the Magisk log, fast thumb drags froze the UI<br>for up to several seconds per frame.<br>When the target is more than a viewport away, jump to the matching<br>item index with scrollToItem() instead; shorter moves still scroll<br>by pixels so slow drags stay smooth.<br>Assisted-by: Claude Opus 5.5

> app: keep dpad focus in content on rail<br>With a navigation rail there is nothing below the page, yet pressing<br>DPAD_DOWN on the last focusable item let the 2D focus search leave<br>the page and land on a rail item to the side. Cancel downward exits<br>from the page in rail mode; moving to the rail is still possible<br>with DPAD_LEFT. The bottom bar keeps its existing focus handling.<br>Assisted-by: Claude Opus 5.5

> app: use bar when navigation rail does not fit<br>The navigation suite switches to a rail once the window is at least<br>480dp tall, but the collapsed rail with the FAB header needs about<br>476dp of its own height for all five destinations plus the 44dp<br>bottom space. In short freeform windows on desktop the last rail<br>item was clipped by the window edge.<br>The rail cannot scroll and its spacing is fixed, so fall back to the<br>short navigation bar when the height left for the rail after system<br>bars is below 520dp, the same switch the library already makes for<br>windows under 480dp.<br>Assisted-by: Claude Opus 5.5

> app: align search fields with app grids<br>On wide windows the DenyList and Grant search fields were centered<br>within their 720dp cap, while the app grid below them starts at the<br>left edge. With few results the cards sat far left under an indented<br>search field.<br>Keep the 720dp cap, which is the M3 search bar maximum, but align the<br>field to the start so it lines up with the grid and the top app bar<br>title. Compact windows are unchanged since the field fills the width.<br>Assisted-by: Claude Opus 5.5

> app: refine FAB slot in navigation rail<br>M3 specifies that a FAB nested in a navigation rail rests at<br>elevation level 0. Use the library's zero elevation for the FAB in<br>the rail header; the FAB floating above the bottom bar keeps its<br>default elevation.<br>The rail header reserves a 56dp slot so the rail items do not jump<br>when the FAB shows or hides. Without root, neither the Modules nor<br>the Superuser tab exists and the FAB never shows, so skip the slot<br>and let the rail items start at the top.<br>Assisted-by: Claude Opus 5.5

> app: use non-deprecated window size class API<br>WindowWidthSizeClass is deprecated in window-core 1.5. Check the<br>width breakpoints with WindowSizeClass.isWidthAtLeastBreakpoint()<br>instead. The adaptive library only buckets widths at 600 and 840dp,<br>so the expanded and compact checks behave exactly as before.<br>The API is only available since window-core 1.4, while adaptive<br>1.1.0 puts 1.3.0 on the compile classpath. Depend on window-core<br>1.5.0 explicitly, the version already resolved at runtime, so the<br>packaged dependencies do not change.<br>Assisted-by: Claude Opus 5.5

> app: size install dialog for wide windows<br>The install dialog always covered the whole window. Full screen<br>dialogs are meant for compact windows only; on a desktop window it<br>turned a short list of options into a huge empty page. Keep it full<br>screen on compact windows, and show it as a regular sized dialog with<br>rounded corners and the dialog surface color everywhere else.<br>Assisted-by: Claude Opus 5.5

> app: use two columns on wide screens<br>Home and Settings are columns of cards, which became very wide and<br>sparse on large windows. Add a small AdaptiveColumns helper that<br>splits the content into two equal columns on expanded width windows,<br>capped in width and centered, and falls back to the existing single<br>column otherwise. Settings wraps each title and card pair so they<br>stay together, and moves the App section to the second column when<br>the root-only sections are hidden.<br>The Superuser detail page only has a few rows, so cap its width and<br>center it instead of splitting it.<br>Assisted-by: Claude Opus 5.5

> app: use grids for app lists<br>The DenyList and Grant Superuser screens listed every app as a card<br>spanning the whole window, and the search field stretched across it<br>too. Show the apps in adaptive grids instead (staggered for DenyList,<br>whose cards expand to show processes), and cap the search field at<br>the Material search bar maximum width. Phones still get one column.<br>Assisted-by: Claude Opus 5.5

> app: show tab lists as adaptive grids<br>On wide windows the Superuser, Modules and Superuser log lists were a<br>single column of cards stretched across the whole window. Turn them<br>into lazy grids with adaptive columns: one column on phones, more as<br>the window gets wider. Modules use a staggered grid since its cards<br>expand, with a larger minimum width for the action buttons row. The<br>spacer items move into content padding so phones look the same.<br>The Magisk log is read from top to bottom, so it stays a single<br>column, but its cards and the log tab row are capped to a readable<br>width and centered.<br>Assisted-by: Claude Opus 5.5

> app: use adaptive navigation suite<br>The bottom navigation bar was used at every window size, which wastes<br>vertical space and looks out of place on wide windows such as desktop<br>and unfolded foldables.<br>Switch MainScreen to NavigationSuiteScaffold, which shows the same<br>bottom bar on compact windows and a navigation rail on medium and<br>wider windows. With a rail, the FAB moves into the rail header; its<br>slot is kept even when the FAB is hidden so the rail items don't jump<br>when switching tabs. > app: support any scrollable in scrollbar<br>The scrollbar only had adapters for ScrollState and LazyListState, so<br>lazy grids could not use it. > Support patching Aluminium OS recovery images<br>Add RecoveryGptProcessor, a WholeFilePatcher for GPT disk images<br>such as Aluminium OS recovery_image.bin. The input is processed in a<br>single sequential pass: all data is copied to the output until<br>init_boot_a is reached, which is extracted for the standard Magisk<br>boot image patch. After the patched init_boot_a is written, the rest<br>of the input is copied. vendor_boot_b is always patched to disable<br>data wipe and AVB hash verification whenever it is encountered.<br>Subclasses can override onInitBoot and onVendorBoot to customize how<br>these images are handled.<br>The vendor_boot patching logic is implemented in app_functions.sh as<br>patch_al_vendor_boot, so it is also available without root access.<br>PatchFileClassifier now detects GPT images as RecoveryGpt, both raw<br>and within recovery zips. MagiskInstaller generalizes whole file<br>processing over WholeFilePatcher, which is now Closeable to release<br>resources when patching is aborted before finish.<br>Add testRecoveryGptProcessor in AppTest, which streams and inflates<br>the recovery image from a remote zip, verifies the checksums of<br>init_boot_a and vendor_boot_b without patching, and verifies the<br>output is identical to the input with streaming checksums.<br>Assisted-by: Claude Opus 5.5

> app: do not show toast on in-app superuser grant<br>Toggling or granting superuser privileges within the Magisk app (such<br>as in SuperuserViewModel or SuperuserGrantViewModel) displayed a toast<br>message confirming the grant or denial.<br>Because the user is already interacting directly with the UI where the<br>state is visible, these toast messages are redundant. Toast messages<br>should only be displayed when a process actually requests superuser<br>access via the su daemon.<br>Remove the toast notifications shown during in-app superuser policy<br>changes.<br>Assisted-by: Gemini 3.8 Flash

> app: fix trackpad scrolling on Googlebook<br>On Android 14+ (including Aluminium OS on Googlebooks), trackpad<br>two-finger scroll gestures are dispatched as MotionEvents with<br>CLASSIFICATION_TWO_FINGER_SWIPE. Compose UI 1.12 translates these into<br>PanMove pointer events with panOffset.<br>However, compose-foundation was not explicitly declared and was resolved<br>transitively to 1.10.0 via compose-material3. In foundation 1.10.0,<br>TrackpadScrollingLogic did not exist yet, causing two-finger swipe<br>gestures to be dropped and leaving scrollable views unresponsive.<br>Add explicit compose-foundation and compose-animation dependencies<br>aligned with compose-ui (1.12.1) so all core Compose modules stay in<br>sync and trackpad scrolling is handled properly.<br>Assisted-by: Gemini 3.8 Flash

> Classify patch input files with PatchFileClassifier<br>Add ZipChannel, a zip archive backed by a DataChannel. open() returns<br>a random access DataChannel of STORED entries, and openStream()<br>returns a sequential stream of STORED or DEFLATED entries.<br>Add PatchFileClassifier to inspect the format of input files and<br>locate the payload to patch: RawFile, BootZip, PayloadBin, or Tar.<br>Zip archives are inspected with ZipChannel, and nested zips such as<br>the inner image zip of factory images are transparently inspected<br>instead. The payload is accessed as either a DataChannel or a<br>decompressed InputStream based on its type.<br>MagiskInstaller now relies on PatchFileClassifier to process inputs.<br>WholeFilePatcher now accepts an InputStream, as whole file formats<br>are always processed sequentially. ZipExtractor is removed as it is<br>fully superseded.<br>Add unit tests for ZipChannel with in-memory zips, and update<br>existing tests to go through PatchFileClassifier.<br>Assisted-by: Claude Opus 5.5
